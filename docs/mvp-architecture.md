# 餐饮私域扫码点餐 MVP — 业务与架构方案（v3）

> `001` 分支的 MVP 规划基线。定位：**面向餐饮的「私域友好」扫码点餐 + POS**，后端 Supabase，微信小程序真机。
> **v3 核心变更（相对 v2）**：① 定位从「即时下单业态通用」收敛为 **餐饮私域**；② 支付从 mock 升级为 **真·微信支付（服务商模式，资金直清商户，无二清）**；③ 新增 **会员 + 储值 + 券** 作为护城河核心；④ 增加商业化 / 上海冷启动 / 合规红线 / 证伪线。技术底座（Supabase / POS SPA / 小票 / 沽清 / 状态机）不变。变更清单见 [附录B]。

---

## 一、定位（一句话）

**卖的不是「扫码点餐软件」，是「帮餐饮老板把到店客变成他自己的会员和储值卡」的私域底座。**
点餐是**钩子**（高频、刚需、零教育）；**会员池 + 储值余额是护城河和现金流**；微信支付**分润**是无感赚钱管道，且商家生意越好、储值越多，服务商才赚越多——**利益完全对齐**（区别于美团「你赚我抽」）。

### 差异化 vs 美团扫码点餐
美团扫码把「已经坐进你店里的客」喂进美团池子：商家拿不到顾客微信/手机号、复购入口在美团首页、点餐页给顾客推竞对、数据只给结果不给资产。
**我们相反**：同一次扫码，顾客进的是**商家自己**的小程序 → 无感沉淀成商家的会员/储值卡 → **不抽佣、不碰顾客数据、不推竞对**。价值主张：**「扫码点餐，但顾客和数据 100% 归你。」**

## 三、业务闭环（v3，含真支付 + 私域沉淀）

```
顾客(小程序)                                     门店(POS SPA)
 ① 扫桌码 → 解析门店+桌(开/接会话)
 ② 浏览 → 加购 → 提交(下单 RPC, status=created)
 ③ 微信支付：Edge Fn 统一下单 → wx.requestPayment
    ├─ 余额充足可选「余额支付」(内部记账，不走微信)
    └─ 微信支付成功 → 微信回调 Edge Fn(wxpay-notify)
        · 验签 → 订单 paid(pay_order) · 无感建/更新会员(openid+手机号)
 ④ 支付成功页 = 私域转化主战场(不改点餐流程)：
    「已成为会员」/「关注公众号领券」/「充100送20 本单立减」
                                    ─Realtime─▶ ⑤ 待接单队列(paid)
                                                │ ⑥ 前台接单 → 打印(后厨单+顾客联)
                                                │ ⑦ 后厨看纸做菜(零操作)
                                                │ ⑧ 前台点完成
 ⑨ 轮询看进度 / 已完成 ◀───────────────────────┘
支线·储值：会员充值(走微信支付,直清商户号) → 余额入账 → 后续余额支付零手续费
异常：前台支付后可取消整单/单项 → refunded；翻台「清台」关闭会话
```

### 订单状态机（同 v2）
`created ──微信支付成功──▶ paid ──前台接单(打印)──▶ processing ──前台完成──▶ completed`
分支：`cancelled`（支付前/created 超时）、`refunded`（支付后取消，走微信支付退款）。
> **`paid` 由微信支付回调驱动**（不再是 mock 点击）；打印仍是接单副作用、不进状态机；流转用条件更新防重。

## 四、微信支付架构（真支付，无二清）

**模式：微信支付服务商模式（服务商 + 特约商户）。资金由微信/持牌方直清到商家自己的特约商户号，平台不碰资金池、不做二清（刑事红线）。** 平台收入 = 微信官方给服务商的**交易分润/返佣**（商户无感）。

```
小程序 ──调用──▶ Edge Function: wxpay-create ──▶ 微信支付 统一下单(JSAPI)
   ◀── prepay 参数 ──                              (mchid + APIv3密钥 + 证书，仅在 Edge Fn)
小程序 wx.requestPayment(唤起微信支付)
微信支付 ──异步回调──▶ Edge Function: wxpay-notify ──验签──▶ 订单 paid + 沉淀会员
```

- **两个 Edge Function**（Supabase Functions，天然 HTTPS 回调地址，解决微信回调必须公网 HTTPS 的要求）：
  - `wxpay-create`：拿订单金额 + openid，调微信 JSAPI 统一下单，返回 `prepay_id` 及签名参数。
  - `wxpay-notify`：接收微信支付结果回调 → **验签 + 解密** → 幂等地置订单 `paid`（调 `pay_order`）→ 无感 upsert 会员（openid + 手机号）。
- **密钥安全**：`mchid`、APIv3 key、商户私钥/证书、`APPSECRET` **只作为 Supabase Function Secrets**，绝不进小程序、绝不入库。
- **退款**：`refunded` 时由 Edge Function 调微信支付退款 API（需商户证书）。
- **分润**：服务商模式下由微信按政策返佣（与交易量/等级挂钩），无需额外下单代码；如需主动分账用微信「分账」API（P1 后置）。
- **openid/手机号**：小程序 `wx.login` 换 openid；支付成功页用微信官方「手机号快捷验证」控件一键授权 → 存 `member`。

## 五、会员 + 储值 + 券（护城河核心）

**设计铁律：顺势不打断。** 点餐流程一字不改，私域动作全塞进**支付成功后的结果页**（顾客已达成目的、最放松）。

- **会员（无感建档）**：支付授权拿到 openid+手机号即自动建会员，记累计消费/到店次数/常点/余额。**这就是美团死活不给商家的资产。**
- **储值（核武器）**：
  - 顾客充值 = 一笔**微信支付交易**（直清商户号），你**提前一次性吃到分润**；余额消费走**内部记账、零手续费**（对商家是省钱卖点）。
  - 老板爱：预付锁客（卡里有钱→屏蔽美团和隔壁）+ 现金流前置 + 拉高频次客单。顾客充：`充100送20 本单立减` + 储值专属价/免排队/生日权益。
  - **合规**：限**单店可用、不可跨店、不可提现、小额**（规避《单用途商业预付卡》监管）；余额可查、明细透明、支持退。
- **券**：满减/代金/新客券，发放入口=支付成功页 + 公众号；提交订单时后端校验核销。

## 六、私域护城河（四层，越用越厚）

1. **会员数据池**（换系统=会员关系归零，openid 绑主体）→ 2. **储值余额（最硬：店里一堆顾客有余额，老板不敢换系统）** → 3. 运营习惯（召回/营销长在你系统）→ 4. 多门店/连锁通用。
> 对比「纯点单收银」零迁移成本必死——**私域的墙 = 顾客的钱和关系都沉淀在你这**。故产品重心压在会员+储值，而非把点餐做花哨。

## 七、数据模型（v3 = v2 + 会员/储值/券）

v2 表（store / service_point / dining_session / category / item / orders / order_item / order_counter）保留，`orders` 增 `member_id`（下单/支付时关联）。新增：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `member` | id, store_id, openid, unionid, phone, balance(numeric), total_spent, visit_count, last_visit_at, created_at；`unique(store_id, openid)` | 会员档案 = 商家私域资产；`balance` 为储值余额 |
| `stored_value_txn` | id, store_id, member_id, type(`topup`/`consume`/`refund`/`gift`), amount, balance_after, order_id(nullable), wx_transaction_id, created_at | 储值流水（充值/消费/赠送/退款），可审计 |
| `coupon` | id, store_id, member_id(nullable), kind(`full_reduce`/`cash`/`new_user`), threshold, value, status(`unused`/`used`/`expired`), expire_at | 券 |

- `member.balance` 只经 **RPC + 储值流水** 变更（不允许前端直改）；充值/退款金额以微信支付回调为准。
- 顾客端 RLS：`member` 只能凭 openid（经 RPC）读自己那条；余额变更全走 `security definer` RPC。

新增 RPC（延续 P0 风格，security definer）：`topup_member`（充值成功回调调用，入账+写流水）、`pay_with_balance`（余额支付，原子扣减+校验）、`get_member`（凭 openid 查会员+余额）、`issue_coupon`/`redeem_coupon`。

## 十二、商业化（先打预防针）

**单店一个月约赚 100–400 元**（分润薄 + 不抽佣）→ **这是「零边际成本铺 1000 家」的规模生意，不是榨单店**。

- **盈利排序**：微信支付**交易分润**（藏着、商户无感、随流水涨）> **储值**（充值一次性分润 + 锁客做大流水 + 现金流）> SaaS 月费（后置、锚定「省下的美团抽成」，99/月）> 云小票机（成本价、当留存钩子）。**抽佣=找死，不做。**
- 单店经济账（月流水 20 万样板店）：分润 ~40–100 + 储值通道分润 ~8–20 + （可选月费 99）≈ 100–400 元/月。CAC（地推）~800–1500 元 → **回本 5–10 个月，靠留存赚长钱**。

## 十三、上海冷启动

- **主攻**：社区高频快餐/茶饮/面馆米粉（客单 20–60、复购强、翻台快）+ **老板亲自盯店、已有私域意识**（门口贴「加微信领券」）+ 新开 1–3 个月的店。
- **避开**：大连锁/有总部 IT、纯外卖、低频正餐、不玩手机的夫妻店。
- **打法**：打透一条街（密度带口碑）→ 创始人亲签前 10 家 → 前 3 月免费 + 送云小票机 → 转介绍裂变。**用付费试点验证生意，不是免费验证程序。**
- **地推第一句**：「老板，美团扫码顾客扫完进的是美团、以后给他推隔壁家；我这套顾客扫码进你自己的小程序，加你微信、存你会员卡、数据全归你，还不抽你一分佣金，两分钟免费装，今天就能用。」

## 十四、合规红线（触一条可入刑/清零）

1. **绝不二清**：储值/支付资金必须走微信支付**服务商模式直清到商家特约商户号**，**一分钱都不经过平台账户**。
2. **储值 = 单店小额、不可跨店、不可提现**（规避预付卡监管）；平台仅提供记账工具，不兜底、不做资金担保。
3. **微信生态规则 > 美团风险**：用官方「支付后关注公众号」「订阅通知」组件，不诱导；企业微信触达合规。
4. **数据归商家**：明确授权收集手机号/openid，不转卖、不用于给商家推竞对，写进隐私政策与商户合同（也是差异化背书）。
5. **别在美团页面/外卖包装内导流私域**（会被限流封店）；私域只在自己堂食场景/自有渠道做。

## 十七、风险清单

- **支付资质门槛**：成为微信支付服务商需企业主体 + 合规进件，非代码能解决，是真支付的最大前置。
- **二清刑事风险**：架构必须资金直清商户，平台不碰钱（已在四节/十四节固化）。
- **储值跑路信任**：钱在商家自己微信账户、不经平台；单店小额；余额可退。
- **微信封号**：重度依赖微信生态，严守官方组件与频率规则。
- **单店 ARPU 低**：靠规模与留存，冷启动 CAC/留存/自传播是生死线（见证伪线）。

---

## 十八、证伪线（试点 3 个月，达不到转纯 SaaS 收费，别硬扛）

- 装机店 3 个月留存 **< 50%** ❌
- 开通储值的店 **< 25%**，或有储值店顾客充值率 **< 5%** ❌
- 微信支付服务商**分润通道拿不到 / 到手 < 万分之1** ❌（地基塌 → 商业模式不成立）
- 单店 CAC **> 2000** 且转介绍占比 **< 10%** ❌（规模化不可能）
